# 2026-07-30 23:14 - Hot Reload

## Goal

Implement `plans/020_hot_reload.md`: remove the edit-to-see-it friction when
developing components. Before this, a one-line change in `templates/` required
re-running `bin/seed_preview`, which reinstalls every component.

## Changes

Phase A - gem development (code):

- Added `bin/watch`. It polls `templates/`, `registry/`, and the install
  templates (156 files), copies each changed file to its single destination in
  the seeded preview app, and bumps a reload token. A registry change is the
  one case that cannot map to a single file — it can add or remove components —
  so it triggers a full reinstall instead.
- Added `scripts/template_sync.rb` holding the path mapping. It lives in
  `scripts/` rather than `lib/` because the gemspec ships only `lib`,
  `registry`, `templates`, and `docs`; this follows the existing
  `scripts/performance_check.rb` precedent.
- `bin/seed_preview` now emits the browser-reload plumbing: a
  `components#reload_token` action, its route, and a small polling snippet in
  the preview layout. This is why controller edits feel hot at all — Rails
  reloads Ruby and ERB on the next request, but a Stimulus controller is a
  module the browser has already fetched, so it is only re-evaluated after a
  page reload.

Phase B - host apps (documentation):

- Added `docs/hot_reload.md` and a short README section. No code: after
  `senren add` the components are ordinary Rails code that Rails already
  reloads. The single real gap is that Stimulus controllers need a page
  refresh, which is documented along with the Turbo 8 morphing implication for
  `disconnect()`. Shipping a watcher or a websocket into every host app to
  automate a refresh was rejected as disproportionate.
- `CONTRIBUTING.md` documents `bin/watch` in the local setup flow.

## Validation

- PASS `bundle exec rake test` — 99 runs, 1887 assertions (was 91 / 1863)
- PASS `bundle exec rubocop --cache false` — 126 files, no offenses
- PASS `bun run controllers:check`
- PASS `bin/performance`
- PASS gem packaging check: 187 files, no `bin/`, `scripts/`, or `test/` entries,
  and the reload snippet appears in nothing that ships.

Functional verification of the watcher against a throwaway preview root
(`SENREN_PREVIEW_ROOT`), since `.local/` is gitignored:

- Reload token written at startup.
- `touch templates/components/button/button_component.html.erb` → copied to
  `app/components/senren/button_component.html.erb`.
- `touch templates/controllers/dialog_controller.js` → copied to
  `app/javascript/controllers/senren/dialog_controller.js`.
- Token changed between the two syncs, so the page would reload.
- `touch registry/components.yml` → full reinstall: 125 component files,
  25 controllers, 62 components, registry mirror written.
- Deleting a watched file logged `gone` and the watcher kept running.

## Decisions

1. Polling rather than the `listen` gem. The scan is ~156 `File.mtime` calls
   per tick, and avoiding a native-extension dependency matters more for a gem
   whose selling point is a thin dependency surface. Interval is configurable
   via `SENREN_WATCH_INTERVAL`.
2. Reload signalling through a token file plus a polling endpoint, not SSE or
   ActionCable. It needs no dependency and no long-lived connection, and the
   entire mechanism lives in the gitignored preview app.
3. `installed_components.yml.tt` is deliberately excluded from the sync map.
   That file is a template for a ledger, and the ledger is state — copying over
   it would erase the install history. There is a test asserting this.
4. Phase B is documentation, not code. Rails already reloads what the host app
   owns; the honest deliverable is telling developers which single case does
   not reload and why.

## Follow-up: `bin/ci` was unrunnable outside Linux CI

Reported by running `bin/ci` on macOS: all 10 system tests errored with
`Errno::ENOENT - /usr/bin/chromedriver`.

`test/application_system_test_case.rb` defaulted `SENREN_CHROMEDRIVER` to
`/usr/bin/chromedriver` and always constructed a `Service` with it. That path
exists on the Linux CI image and nowhere else, so the suite could only run on a
developer machine if the contributor happened to know to set two environment
variables. My earlier verification missed this because I set those variables
myself rather than running `bin/ci` the way a contributor does — the tests
passed, but for a reason no one else would reproduce.

Fixed by only passing an explicit `Service` when a driver actually exists, and
otherwise letting Selenium Manager (bundled with selenium-webdriver 4.44)
resolve and download a matching driver. Added the macOS Chrome locations to the
binary candidates. Linux CI behavior is unchanged: `/usr/bin/chromedriver` is
still found and used.

Verified with `env -u SENREN_CHROMEDRIVER -u SENREN_CHROME_BIN bin/ci`:
all five steps pass, 10 system runs / 139 assertions, no environment setup.
`docs/performance_testing.md` now says the variables are an override, not a
requirement.

## Bug found while testing

The full-reinstall path copied the registry mirror into `.senren/` without
creating the directory first, so it raised `Errno::ENOENT` on a preview app
that had never been seeded. `bin/seed_preview` does the `mkdir_p` itself, which
is why the omission was invisible until the watcher was exercised against a
bare directory. Fixed by calling `paths.ensure_dirs!` before the copy.
