# 2026-10-08 00:30 - Hold json below 3 so the Rails matrix passes

## Goal

`bin/matrix` failed `test:integration` on `main` (4aab71e) for Rails 7.1, 7.2
and 8.0 with `ArgumentError: unknown keyword: quirks_mode`. Rails 8.1 was green.
The other red gate on `main`, the rubyzip audit (CVE-2026-85396), is fixed by
the open PR #26 and is left out of this change.

## Changes

- `gemfiles/common.rb`: `gem 'json', '< 3'` in the shared development group,
  with a comment naming the call site and when it can be lifted. The root
  `Gemfile.lock` gains the matching `json (< 3)` line under DEPENDENCIES; the
  locked json stays 2.21.2.
- `CHANGELOG.md`: one entry under Unreleased / Internal.

## The json root cause

The call site is ActiveSupport, not this gem and not a test:

```
activesupport-8.0.5.1/lib/active_support/json/encoding.rb:110
  ::JSON.generate(jsonified, quirks_mode: true, max_nesting: false)
```

`JSONGemEncoder#stringify` runs whenever a tag option holds a hash or array
(`ActionView::Helpers::TagHelper::TagBuilder#prefix_tag_option` -> `to_json`).
json 3.0 removed `quirks_mode:`, so every such render raised.

Where it reproduces, checked in the installed gems and on pristine `main` with
the lockfiles from before this change (`test:integration`, 63 runs each):

| Rails | activesupport | passes `quirks_mode:` | before |
|---|---|---|---|
| 7.1 | 7.1.6 (latest of the series) | yes | 4 failures, 26 errors |
| 7.2 | 7.2.3 | yes (7.2.4 does not) | 4 failures, 26 errors |
| 8.0 | 8.0.5.1 (latest of the series) | yes | 4 failures, 26 errors |
| 8.1 | 8.1.4 | no | 251 assertions, 0 failures |

Why only some lockfiles had json 3: `gemfiles/*.gemfile.lock` are not committed
(`.gitignore`: they are resolved per job, because one lockfile cannot satisfy
Ruby 3.2 to 3.4). A fresh resolve picked rubocop 1.91.0, whose gemspec says
`json (>= 2.3)`, where rubocop 1.86.1 (still in the committed root lockfile)
says `json (~> 2.3)`. That let Bundler choose json 3.0.2. The root bundle never
saw it, so `bin/ci` tests were green while `bin/matrix` was red, and the CI
matrix resolves every job fresh, so it would reach the same json.

## Decisions

- Constrained json instead of upgrading the caller. Only 7.2 has a fixed
  ActiveSupport (7.2.4); 7.1.6 and 8.0.5.1 are the last releases of their
  series and still pass `quirks_mode:`, so a json pin is needed whatever 7.2
  does. One constraint in `gemfiles/common.rb` covers the root bundle and every
  per-Rails gemfile, and keeps the declaration in the one place the file says
  dev dependencies live.
- The constraint is on the development bundle only. The gemspec does not mention
  json, and a host app on Rails 7.1 or 8.0 with json 3 hits the same Rails bug
  with or without this gem.
- Left rubyzip to PR #26, which already carries the same lockfile change.
- Left the per-Rails lockfiles' own Rails advisories alone. `bundle-audit check
  --gemfile-lock` on the local 7.1 and 7.2 lockfiles reports ActionView,
  ActiveStorage and ActiveSupport advisories for Rails 7.1.6 and 7.2.3. They are
  the versions under test, CI audits only the root bundle, and 7.1 has no fixed
  release; recorded here so it is not a surprise later.

## Next steps

- Lift the json constraint once the matrix no longer includes a Rails that
  passes `quirks_mode:` (7.1 and 8.0 have no fixed release; raising the 7.2 floor
  to 7.2.4 only helps that series).
- Merge PR #26 for the rubyzip advisory.
